# 検証結果：RAG と LLM Wiki の知識参照

- 対象レベル：実践
- このページで分かること：8B 級ローカルLLMで RAG と LLM Wiki を動かしたときの、参照の確認方法・失敗の仕方・改訂への強さの違い
- 最終確認日：2026-11-08（Ollama 0.40.14、granite3.3:8b、granite-embedding:278m）

手順とスクリプト：[labs/01-knowledge-reference-check](../../labs/01-knowledge-reference-check/README.md)

## 1. 環境

| 項目 | 値 |
|---|---|
| 端末 | Apple M1、メモリ 16GB（GPU 利用可能 11.8GiB） |
| 実行基盤 | Ollama 0.40.14（localhost のみ、クラウド機能無効） |
| 生成モデル | granite3.3:8b（Q4_K_M、4.6GiB、Apache 2.0。ベースモデル Granite 3.3 8b Base） |
| 埋め込みモデル | granite-embedding:278m（Apache 2.0、日本語対応、入力上限512トークン） |
| 設定 | コンテキスト長 16384、KV キャッシュ q8_0、Flash Attention、temperature 0 |

## 2. RAG の結果

| ID | 結果 | 要点 |
|---|---|---|
| RAG-01 | 合格 | RAG ありは正答・正しく引用（入力437トークン）。なしは「エラー」ともっともらしく捏造（入力55トークン） |
| RAG-02 | 合格 | 取り違えやすい資料が検索されても流用せず「記載なし」。ただし文言は指示どおりではなかった |
| RAG-03 | 合格 | 引用0件を合格と判定していたキットの不具合を修正 |
| RAG-04 | 合格（再試験） | 検索は正常。引用が `[ID]` の書き写しになったが、見本付きの指示で解消 |
| RAG-05 | 失敗を再現 | 入力468→130トークンに警告なく切り捨て。指示と正解資料が消え「HR-」と誤答 |
| RAG-06 | 弱点を再現 | 改訂資料が検索に入った質問は新しい値、入らなかった質問は古い値。判定はどちらも OK |

| WIKI-03 の試行 | 結果 |

## 4. 比較

| 観点 | RAG | LLM Wiki（8B 級） |
|---|---|---|
| 準備の手間 | 索引化のみ（数秒） | 取り込み1本 42〜134 秒。資料が増えるほど増加 |
| 参照の追いやすさ | 高い | 高い |
| 改訂への対応 | 検索しだいで古い値 | 矛盾は検出できるが、反映は不安定 |
| 最大のリスク | 古い値の回答が正常に見える | 保守のたびに知識を壊しうる。誤りが残り続ける |
| 規模の拡張性 | 高い | 既存ページを全件渡す方式では成立しない |

## 5. 知見

1. 参照の確認は、カナリア値と入力トークン数（`prompt_eval_count`）でできる
2. コンテキスト長は明示し、サーバーログ（`truncating input prompt`）で切り捨ての有無を確認する
3. 引用の判定は「範囲内か」まで。古い資料の引用や引用先の取り違えは検出できない
4. 小型モデルへの指示は見本付きで具体的に書く
5. 台帳（目次・出典・ファイル名）は機械に任せ、LLM には本文だけを書かせる
6. LLM Wiki は前回の出力が次の入力になるため、ゆらぎが連鎖して増幅する
7. 8B 級モデルは矛盾を「検出」できても、知識を安全に「更新」できない。更新は人のレビューを前提にする
8. 改訂への弱さは両方式に共通。根本対策は文書の版管理
